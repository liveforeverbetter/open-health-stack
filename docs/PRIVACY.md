# Privacy model: what this prototype lets one person verify

## The claim

For reads made through the reference monitor (the CLI and the MCP stdio server), the person can verify on their own device that:

1. **Every read is on record.** Each tool call, allowed or denied, and each import is written to the access log in the same SQLite transaction as the read. If the log entry cannot be written, the call returns nothing.
2. **Every read stayed inside the granted scopes.** A tool runs only if all its declared scopes were granted to the session, and while it runs the SQLite authorizer lets it read only the tables of those scopes. The tables it actually read are recorded, and the verifier re-checks them against the declared and granted scopes.
3. **The record has not been altered.** Deleting, editing, reordering or appending entries, or rolling back the database alone, is detected by the hash chain plus the device witness.
4. **Nothing left the device.** The package imports no networking or process modules (checked by a test), and a runtime audit hook blocks and counts socket, HTTP, subprocess and native-library events. CI also runs the pipeline in a container with networking disabled.

## Against whom

| Adversary | Covered? |
|---|---|
| An assistant that asks for more than it was granted, including because of instructions hidden in a document | Yes: refused and logged (`out_of_grant` in the suite) |
| A tool implementation that declares one scope but queries other tables | Yes: blocked by the authorizer and logged (`rogue_tool`) |
| Someone who can edit `store.db` but does not hold `device.key` | Yes for edit, delete, reorder, forged append, database rollback |
| Someone who restores old copies of **both** `store.db` and `witness.json` | **No** (`rollback_all`; see Known gaps) |
| Someone who holds `device.key` or controls the device or Python process | No |
| What an assistant's provider does with answers it legitimately received | No; that is "sharing" (OSF line 04), out of scope here |

## How to check it yourself

```sh
wellnizz-local verify            # chain, witness, scopes
wellnizz-local log --tail 50     # read the record
./reproduce.sh                   # rerun the red-team suite on synthetic data
```

## Known gaps (the research agenda)

- **Rollback of database and witness together.** The witness is a file; an attacker can restore an older valid pair. Fix: keep the witness counter in a monotonic hardware counter (TPM 2.0 NV counter, secure element) or countersign the head with an external witness the person controls.
- **The device key is a file.** Moving it into a TPM, secure element or FIDO2 token is planned.
- **In-process confinement.** Tools run in the monitor's Python process. The authorizer is checked on every statement (statement cache disabled), but Python code in the same process could in principle reach around it, for example from a background thread. Process isolation (a separate tool process with only a read-only, scoped view) is the next step.
- **Reads that bypass the monitor.** Opening `store.db` with another program is not logged. Encrypting the store under a key only the monitor can unwrap would close this; it is not done yet.
- **Attestation.** The person cannot yet check that the monitor they talk to is the build in this repository. Reproducible builds plus remote attestation are future work.
- **Audit hooks are not a sandbox.** They stop Python-level network calls in this process, not native code or other processes.

## Cost in usefulness

The monitor adds well under a few milliseconds per call on a laptop (the suite reports the median; on the development machine on 23 Nov 2026 it was about 0.9 ms). Scope grants are coarse (three scopes); finer grants would cost more user decisions per session.

## Data used

Only synthetic data generated by `synth.py` from a seed, and a bundled 8-position reference set from NCBI dbSNP (public domain). No real person's data is used, stored or published.
